# 前端架构参考实现完善设计

基线为 `ff4edaf` 和工作区已完成的首页简化。项目以在线书店的只读目录展示现代前端架构。中英文首页的架构概览正文随预渲染外壳返回，公共布局可增强语言切换和主题控件。书籍目录可以直接浏览、筛选、翻页和进入详情。演示模式使用独立 SQLite 种子。两种模式都保留只读目录场景，关键词搜索仅在演示模式可用。首页和业务页面的文案采用介绍和实际状态反馈，项目运行指引放在仓库文档。

## 架构组合

Bulletproof React 的 feature 共置和应用层组合对应本仓 `app → features → shared` 的导入方向。FSD 的 Next.js 指南提供按服务端与客户端拆公开入口的先例。Next.js 的 BFF 指南支持在进程内让 RSC 直接调用数据读取逻辑，由 Route Handler 服务 HTTP 调用方。Cockburn 的端口与适配器对应 `CatalogPort` 的目录适配器。Graça 的 Explicit Architecture 提供按业务组织模块和在边缘接入适配器的组合依据。Vercel Shop 的搜索页是把 URL 状态、服务端取数与 `Suspense` 放在同一条实际交互中的源码参考。

## 目录行为

**目录末页。** 发布模式每页最多显示 12 本。一页不足 12 本或已达公开页码上限 100 时，当前页直接返回。页面未达上限且收到满页时，在同一个 `AbortSignal.timeout(2000)` 下按相同分类和 size 查询下一页。使用已有字段和重复 UUID 校验解析两次响应。读取响应前先判断状态与 JSON 媒体类型。成功响应的已解码正文限制在 256 KiB，该上限为合法的 12 行目录和转义文本留有余量。拒绝超限、错误媒体类型或无效正文并取消相关流。详情的上游 404 仍映射缺失，错误响应不读取上游错误正文。下一页是否有书决定 `hasNext`，结果只返回当前页内容。前探失败按现有 502 或 504 处理，页面显示重试提示。API 形状和 demo SQLite 分页不变。缓存的未命中多一次有条件的上游调用，已缓存的查询仍由页面和 BFF 共享。

**目录来源。** 列表生成详情链接时只携带规范化的 `category`、`q` 和 `page`。详情用目录模型校验这组已知字段，在正常页及已知读失败页生成相同语言的目录链接，重试自身时保留合法参数。详情直接访问时缺少上下文或已知字段非法，回到当前语言的默认目录。忽略详情 URL 上其他参数，禁止把外部 URL 当成导航目标。发布模式舍弃 `q`，使返回链接可用。语言切换复用现有查询保留行为。书籍缺失页保留现有回目录入口。

**404 和键盘。** 支持的 locale 下未匹配路径由 locale catch-all 触发对应 `not-found`。已知业务详情缺失继续用现有本地化缺失页。记录普通未匹配路径的 HTTP 404，保留流式详情可能为 200 的文档说明。键盘测试选择不同分类、通过提交按钮提交并等待结果，验收结果显示、焦点可继续操作、返回或直接访问时控件对应 URL。结果有可见数量或空结果，在同一路径更新已有状态区域的文字。状态文字包含已提交的分类与关键词（如有）。数量相同时修改分类或关键词也会更新文字，空结果有明确信息。测试核对状态节点在一次成功筛选中保持并更新、下次 Tab 到达结果，以及原生 GET 表单和控件仍可用。读屏实测结果单独记录。

## 可观察性与架构约束

在 RSC 和 Route Handler 的请求边界记录已知目录降级和 BFF 的 5xx。日志字段固定为 `event`、`entry`、`requestId`、`code`、`status`、`durationMs`。`event` 为 `catalog.read_failed`，`entry` 取 `api.catalog.list`、`api.catalog.detail`、`page.catalog.list`、`page.catalog.detail`。每次失败的标识由服务端生成。BFF 日志与响应 JSON 共享同一个标识，HTTP 状态和错误格式维持 OpenAPI 契约。通用 HTTP 错误序列化只调用可选的观察回调，目录 entry 和计时由目录入口提供。页面在降级分支记录返回给用户的错误分类。日志只传显式允许的字段。计时覆盖当前入口的处理过程。记录的状态是分类对应的状态，流式页面可能已返回 HTTP 200。缓存键仅使用公开数据维度，日志与请求标识在缓存边界外。

将 feature 的 `client.ts` 公开入口纳入架构图的客户端检查起点，即使没有现有浏览器调用方也检查其运行时依赖。现有 `use client`、别名、传递依赖与 type-only 规则继续生效。对 model 入口和 model 目录源码显式限制全局 `fetch`，包括 `globalThis.fetch`，在规范里写明自动检查覆盖的范围。保持真实的 I/O 在适配器。

## 发布路径与文档

用 Node 24.15.0 Linux 镜像，在共享基础层预先安装 `package.json` 固定的 pnpm 11.25.0。发布容器启动阶段无须包管理器或依赖下载。参考 release 镜像沿用 `pnpm build` 和 `pnpm start`，以非 root 运行，工作目录中提供生成产物、静态资产、配置、启动器及所需安装依赖。镜像打入提交标签。镜像上下文排除 .git、宿主依赖、构建缓存、测试产物、演示数据库和本地环境文件。用目录替身和回环入口验收启动后的镜像。配置正确时 `/api/ready` 返回 200。缺依赖时 `/api/health` 仍为 200，`/api/ready` 返回 503。发布镜像每 PR 由独立 CI job 在内部网络执行烟测。发布指南包含版本标识、烟测与切回上一版本的步骤。回滚演练验证两次不同提交生成的不同镜像 ID，并从同一个访问入口复验切回版本的镜像身份、就绪和目录接口。

恢复现有命令可以复跑的文档。demo 启动使用冻结安装、进程级 `DEMO_DATA_DIR`、`pnpm demo:seed`、`pnpm dev:mock`。发布手册列出运行配置、进程存活与目录就绪的检查方式。在 README、文档索引和测试章节链接对应入口。文档组织参考 [Diátaxis](https://diataxis.fr/)。

## 验收与合并

1. 运行冻结安装、peer、类型、Lint、格式、架构和 OpenAPI 一致性检查。
2. 运行全量 Vitest，验证模型、目录适配器、I/O 约束、错误日志和翻译。使用固定 Linux 环境运行两个生产构建、全量 Chromium E2E 和视觉回归。
3. 用仓库自带的目录替身验证发布镜像的启动、静态资源、健康、就绪和目录响应。
4. 使用测试记录证明当前提交的结果，用 PR 审查实际变更及其验收。检查 PR 最新提交的 CI、合并状态和评论。满足上述条件后合并到 `main`，再核对 PR 的合并结果。

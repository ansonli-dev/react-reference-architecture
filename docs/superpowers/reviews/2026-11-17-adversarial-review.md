## R2 · Java 真实故障

| 反例与证据                                                           | 修订                                                                           | 实施验收   |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------- |
| 补偿先释放，旧 worker 随后完成，或旧预留迟到                         | Order 先 CAS fence、再幂等 release。缺记录也写 tombstone，补偿可恢复           | J4、J5     |
| `KafkaMessageProcessor` 失败分支提前 ack。逐项 handler 吞异常        | v2 事务提交后 ack，失效保留 broker 重投，异常传播                              | J6、J8     |
| 旧消费组误按 legacy 扣减 v2 预留。回退后仍可取消现存订单             | Avro 默认字段标识协议，先新 consumer 后 producer。切流不退回旧 worker、DB/群组 | J6、J8     |
| Better Auth catch-all 允许合法 session 请求凭证或关联信息            | 精确方法/路径 allowlist，禁 account link/token cookie，直接 HTTP 尝试取 token  | J7         |
| fresh Kafka 有 broker 而无 Order relay 和 schema                     | 启用已有 scheduler，Topic/Schema 初始化成为启动前提                            | J1、J6、J8 |
| 黑洞 RPC、重复 PG unique 竞争、预留最后一册后又按库存拒绝            | 有界时限和持久 lease。冲突重读获胜记录。使用已确认预留和冻结报价               | J3–J5      |
| 管理成功后从 Java Redis 读旧标题。旧 HTTP detached writer 覆盖新库存 | v2 查权威库，隔离 legacy profile/DB，共用活跃写路径的事务约定                  | J2、J4、J8 |

R2 未将普通旧 Kafka release 判定为已证实的 detached 写入问题，该处理器由外层事务包围。仍保留与 v2 并发的验证，因为旧 HTTP 和不同配置的 writer 存在不同事务边界。报价也将 CNY 折扣语义与 USD 目录展示分开。

### 评审结论

三位独立 reviewer 对不同版本提出反例，作者逐项核对并修订。R3 的“需修订后实施”针对当时版本，表中修订已应用并检查相应任务。尚待实施的外部证据包括 Java/Kafka/Keycloak 真实启动、两模式浏览器验证和新业务的失败注入。它们是计划门禁，没有在本次文档评审中被标为通过。支付、履约、生产容量和独立扩展示例不占核心交付判定。

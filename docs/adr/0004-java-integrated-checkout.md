# ADR 0004 Java 集成结算

已采用。

## 背景

购物车是读者可以继续修改的草稿，报价则固定了本次交易的书目、数量和价格。发布模式下，读者取得报价后仍然可以修改购物车。下面这笔交易中，两本书各报了 1 本，读者随后把第一本改为 2 本，再确认原报价。[两行购物车联调用例](../../test/live-java/checkout.spec.ts#L637)

| 书目                    | 报价上的数量 | 成交前的购物车        | 原报价成交后                  |
| ----------------------- | ------------ | --------------------- | ----------------------------- |
| Bounded Contexts        | 1 本         | 改为 2 本，行版本更新 | 订单记 1 本，购物车保留 2 本  |
| A Guide to Transactions | 1 本         | 仍为 1 本，行版本相同 | 订单记 1 本，该行从购物车移除 |

## 决策

**按状态的所有者存储。** BFF 通过 Keycloak 登录取得账户身份，在自己的 PostgreSQL 中保存会话、购物车条目，以及报价与草稿行版本的关联。浏览器只持有不透明的 HttpOnly 会话 Cookie。服务端读取目录取得当前书价和库存，调用订单服务创建人民币报价、提交并查询交易。报价、提交、订单和取消记录以订单服务保存的结果为准。[会话](../../src/server/auth.server.ts) · [服务端装配](../../src/server/shop.server.ts) · [草稿表](../../database/cart.sql) · [适配器契约](../../contracts/java/README.md)

**用报价版本决定清理范围。** 修改草稿行数量会生成新版本，由 `ETag` 暴露给浏览器。创建报价时，BFF 核对购物车版本，再把实际参与报价的书籍 ID 和行版本与报价 ID 一起保存。取得 `PLACED` 结果后，BFF 在自己的数据库事务里记录提交状态，并删除仍与报价版本匹配的行。[草稿与成交处理](../../src/server/adapters/java/cart.server.ts)

## 取舍与恢复

订单提交和草稿清理发生在两个系统里，BFF 可能晚于订单服务观察到成交。已知提交 ID 的待处理交易会在读取购物车时重新查询。若提交响应丢失，浏览器以原报价 ID 作为幂等键重试，重新取得提交结果。已处理的终态与草稿清理在同一 BFF 事务中落库，重放时可以保住后来编辑的行。[浏览器提交请求](../../src/features/checkout/api.ts) · [丢响应重试联调用例](../../test/live-java/checkout.spec.ts#L569)

本地演示把下单、扣库存和草稿清理放进同一个 SQLite 事务。发布模式的独立联调用例则通过注入一次操作 `401` 核对真实登录回跳，还覆盖异步提交和成交后按版本清理草稿。两种构建复用页面与同源接口，发布所需的运行配置和服务凭据在处理请求时读取。[BFF 契约](../../contracts/bff/v1.yaml) · [登录恢复联调用例](../../test/live-java/checkout.spec.ts#L437) · [运行配置](../operations/run-and-release.md#java-集成)
